## Схема подключения

Обычный Xray-клиент подключается к публичному адресу входного VPS. WatTunnel **Client** принимает TCP/UDP и передаёт на WatTunnel **Server**, который подключается только к разрешённым портам своего `127.0.0.1`. На выходном VPS нужен существующий Xray inbound. Адрес входного VPS задаётся через существующие настройки Host/подписок; раздел Tunnels не меняет конфигурацию Xray.

Роли не привязаны к стране. **Reverse** меняет инициатора межсерверного соединения: Server подключается к Client, но пользовательский трафик по-прежнему принимает Client.

## Платформы и установка

В комплект входит закреплённый WatTunnel **3.3.0**: Linux amd64/arm64 и Windows amd64. Упаковка проверяет RSA-подпись SHA256SUMS; перед запуском проверяются хеш и версия бинарника. На Windows доступны TCP, UDP, TLS и WSS, включая reverse. ICMP требует Linux и `CAP_NET_RAW`. Панели на остальных платформах могут управлять поддерживаемыми удалёнными нодами.

Linux-установщик создаёт пользователя `x-ui-wattunnel`. При ручной установке:

```sh
sudo useradd --system --no-create-home --shell /usr/sbin/nologin x-ui-wattunnel
```

Root-панель понижает UID дочернего процесса и передаёт только необходимые capabilities. Для непривилегированной панели права нужно предоставить заранее. Панель не вызывает sudo и не меняет firewall/sysctl. В Docker для ICMP нужен `NET_RAW`, для низких портов — `NET_BIND_SERVICE`; также нужно опубликовать выбранные порты или использовать Linux host networking. Рабочие файлы находятся в `wattunnel-runtime` рядом с бинарником. Счётчики движка сбрасываются при перезапуске процесса.

## Настройка двух VPS

1. На выходном VPS создайте Xray inbound, доступный на `127.0.0.1:443`.
2. В Tunnels создайте Server, укажите его публичный адрес, транспорт TCP и порт `4443`. Создайте ключ, разрешите целевой TCP-порт `443`, включите туннель.
3. Экспортируйте токен. Он содержит секретный ключ.
4. На входном VPS отключите генерацию ключа и импортируйте токен. Задайте проброс публичного TCP `8443` в целевой `443`, включите туннель. Параметры соединения берутся из токена, пробросы задаются отдельно.
5. В обычном Xray-клиенте укажите входной VPS и `8443`, сохранив данные авторизации, TLS/Reality и SNI выходного inbound.

Для UDP добавьте отдельное правило на обеих сторонах. TCP и UDP могут иметь одинаковый номер порта. UDP можно передавать внутри TCP/TLS/WSS-транспорта.

Для reverse включите его на обеих сторонах. На Server укажите адрес Client для обратного подключения, на Client откройте порт транспорта. За NAT потребуется доступный извне endpoint. Направление проброса не меняется.

## Auto и диагностика

Auto выбирает доступный транспорт без speedtest. Server принимает настроенный набор, Client использует один транспорт. Начальный порядок: UDP → TCP → TLS → WSS → ICMP. Недоступные платформе варианты исключаются. После рестарта первым проверяется последний рабочий транспорт. Здоровое соединение сохраняется; после 45 секунд без подтверждённого обмена клиент повторяет выбор с backoff. Переключение может оборвать активные подключения. Auto не определяет reverse-peer автоматически и не меняет direct/reverse.

UI отдельно показывает желаемое состояние, процесс/соединение, выбранный транспорт, RTT, wire-трафик, потери и ошибки отправки. Потери — оценка движка; отсутствие клиента на Server не означает неисправность. Недоступная статистика обозначается как неизвестная.

TLS/WSS используют штатную PSK-аутентификацию WatTunnel. Self-signed сертификат транспорта не является публично проверенной идентичностью. При необходимости задайте SHA-256 pin на подключающейся стороне. Формат `wat1:` не переносит pin — его нужно задать отдельно. Пути сертификата и TLS-ключа относятся к целевой ноде; её служебному пользователю нужен доступ. Между пользователем и Xray сохраняйте сквозное TLS/Reality.

## Ноды, ключи и восстановление

Синхронизация секретов допускается только по проверенному HTTPS, pin или mTLS. HTTP и skip-verification для туннелей запрещены. Старая нода сообщает об отсутствии поддержки. Синхронизированный туннель редактируется только владельцем. Изменения и удаления переживают недоступность ноды; после восстановления применяются повторно. Для переноса на другую ноду удалите и создайте туннель заново.

Ключи в БД зашифрованы отдельным keyring: `<XUI_DB_FOLDER>/wattunnel-secrets/keyring.json`. Сохраняйте его защищённую копию вместе с бэкапом БД: одной БД недостаточно для восстановления. Linux использует права `0700/0600`, Windows — закрытые ACL. При потере keyring перехода к plaintext нет. Секреты не передаются через argv или обычные ответы API. Экспорт токена — отдельный административный POST без кэширования.

Metrics остаётся на loopback: не публикуйте этот порт через reverse proxy, поскольку upstream размещает там также debug/управляющие обработчики. Для смены PSK замените ключ на обеих сторонах; независимые стороны автоматически его не согласуют.

WatTunnel обновляется и откатывается вместе с пакетом панели. Stop сохраняется после перезапуска. Delete завершает принадлежащий панели процесс, удаляет его файлы и сохраняет tombstone для offline-нод. Существующий Xray inbound и сторонние установки WatTunnel не удаляются.

## Проверка

```sh
# Только проверка публичного listener, без авторизации Xray:
nc -vz ENTRANCE_IP 8443
# После настройки обычного Xray-клиента:
curl --proxy socks5h://127.0.0.1:1080 https://example.com/
```

Реальные процессы: `WATTUN_E2E_BINARY=/path/to/wattun go test -v ./internal/wattunnel`. Для каскада через Xray также задайте `XRAY_E2E_BINARY`. `make node-e2e` проверяет настоящие панели. Linux CI отдельно проверяет ICMP, Windows CI — свою матрицу транспортов. `scripts/wattunnel-lab.sh` создаёт изолированные network namespace для потерь и блокировок. Лабораторные результаты и реальные испытания маршрутов РФ/Ирана/других сетей учитываются отдельно; имитация блокировки не доказывает обход DPI.

### Изолированный стенд Ubuntu

Образ стенда использует Ubuntu 24.04 и проверенный закреплённый бинарник. Ему нужны права для network namespaces; внешняя сеть отключена:

```sh
docker build -f deploy/test/wattunnel-lab.Dockerfile -t xui-wattunnel-lab .
docker run --rm --network none --privileged \
  -v "$PWD/wattunnel-lab-results:/results" xui-wattunnel-lab
```

Запускайте в одноразовом тестовом окружении. Измерения сохраняются в `results.jsonl`; firewall и потери применяются только внутри двух новых namespaces. В каталоге результатов остаются также случайные тестовые ключи и журналы. Стенд не использует БД панели или существующие настройки сети.
