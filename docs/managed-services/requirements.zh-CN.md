实现中必须覆盖：

对每个新增协议，画出或说明实际数据路径：
客户端 → 协议服务端 → 身份识别/计量/限速 → 路由执行 → 出站 → 目标。

路由要求：
1. 新协议必须进入统一的路由管理流程，按实际能力适配用户、入站、目标域名/IP、端口、TCP/UDP、出站选择、阻断和负载均衡等相关规则。
2. 通过真实请求验证路由结果，包括出口变化、阻断结果和规则优先级，不能只测试规则保存成功。
3. 如果使用内部桥接，必须说明如何保留 client 身份、原始目标地址以及可获取的域名信息。
4. 不能将所有用户汇入一个无法区分身份的内部入口，却声称实现了 per-client 路由或限速。
5. 内部桥接、环回接口、代理链和主从节点之间不得重复计费。
6. 避免路由回环；关键策略或后端失效时，不得静默回退为绕过限制的直连。
7. 无法获取的域名、应用层信息或用户信息，必须如实处理，不能用猜测数据假装规则已执行。

五、SSH Tunnel 与 mieru

SSH Tunnel：

将其实现为可管理的隧道服务，明确面板负责的是 SSH 服务端接入还是到上游 SSH 服务的连接，不能只生成 SSH 命令示例。

默认覆盖标准隧道使用场景：
- 本地转发 -L。
- 动态 SOCKS 转发 -D。
- 远程转发 -R；该能力默认关闭，由管理员显式授权后启用。

同时评估并整合可供统一路由选择的 SSH 上游出口。

要求：
1. 每个 client 具有独立认证身份，并可撤销、禁用、限速、计费和限制额度。
2. 多个 SSH 连接及一个 SSH 连接内的多个 channel，必须归入同一 client 的策略和统计。
3. 支持与所选实现兼容的公钥认证及必要的账号配置，严格校验上游主机密钥。
4. 默认不授予交互式 shell、命令执行、SFTP、PTY、agent forwarding 或其他与隧道无关的权限。
5. 远程监听地址、目标访问范围和反向转发端口必须受控，不能默认暴露无认证的公网代理。
6. 不得破坏宿主机现有管理 SSH；优先使用独立受管实例或等效隔离机制。
7. 清楚区分 TCP 隧道、SOCKS 动态转发和额外 UDP 封装方案，不得把未实现的 UDP 能力标成支持。

mieru：

1. 核对官方 mieru 客户端和 mita 服务端的真实配置、用户模型、统计接口、流量配额及出口能力。
2. 优先复用可靠的原生多用户与统计能力，同时接入 3x-ui 的统一 client ID、限速、倍率和额度执行。
3. 处理原生配额时间窗口与面板额度语义的差异，避免双重扣量或两套策略互相冲突。
4. 对适用的 TCP/UDP 路径分别验证连通、路由、限速、计量和禁用效果。
5. 完成前端、API、部署、升级、日志、订阅或配置导出等整合。

六、所有适用服务的 per-client 限速

限速必须覆盖现有协议及新增的 Snell、SSH Tunnel、mieru、端口转发，不能只给新增协议加字段。

默认语义：
- 上传、下载方向以 client 视角定义，分别可配置。
- 内部统一速率单位，前端明确区分 Mbps 与 MB/s。
- 0 表示该方向不限速；拒绝负数和无效数值。
- 默认不限速，不改变旧用户行为。
- 限制对象是同一 client 的全部并发连接总和，而不是每条连接单独享有完整额度。
- 同一 client 绑定多个实例或转发规则时，按明确的策略作用域合并执行，不能通过增加连接或规则数量绕过限制。
- 两个 client 即使共用公网 IP，也必须分别执行策略。

实现必须落在实际数据路径：
1. 根据后端选择按已认证用户执行的限速器、tc、可可靠分类的内核机制或等效方案。
2. 不得把 IP 限速、整个共享端口限速或整个多用户进程限速冒充 per-client 限速。
3. 对整形和丢包式 policing 作出明确区分。不能只添加简单的 limit/drop 规则，就宣称实现了符合要求的带宽整形。
4. 限速修改应作用于已有连接，明确并测试生效时间；默认验收目标为 2 秒内。
5. 设置有限的 burst、队列和缓冲区，避免无限缓冲、严重饥饿或以断流代替限速。
6. 如果已有多节点共享 client 模型，明确全局与节点级限制。不能让 N 个节点各自分配一份完整限速，却在界面宣称是全局上限。
7. 后端无法执行限制时，必须报错或进入明确的受保护状态，不能静默允许不限速运行。

七、每个 client 的流量计费倍率

为每个 client 提供独立倍率，默认 1，支持正数小数，例如 0.5、1、1.5、2、10。明确允许范围和精度；本次不默认引入倍率为 0 的免费模式。

默认采用上传与下载之和扣减额度：

新增计费流量 = 新增原始计量流量 × 生效倍率

例如：
额度 100 GiB、倍率 2，在没有历史用量且倍率不变的情况下，可使用约 50 GiB 的原始计量流量。

必须实现：

1. 分别保存和展示原始上传、原始下载、计费流量、额度、剩余额度和当前倍率，不能只修改前端显示。
2. 存储以明确的字节和定点单位为基础，界面区分 GB/GiB，避免单位混淆。
3. 倍率在新增流量入账时生效。修改倍率不能追溯重算历史用量：
   已用 10 GiB、倍率 1；改为 2 后再用 5 GiB，累计计费应为 20 GiB。
4. 倍率切换必须有清晰的计量边界或版本标识，不能把切换前后全部未结算流量随意套用一个倍率。
5. 使用定点数、整数比例或其他可证明精度的计算方式，保留小数余量，避免浮点累计误差和逐批四舍五入偏差。
6. 相同流量无论分成多少批上报，最终计费结果必须一致。
7. 明确各后端的原始计量边界：应用有效载荷、协议流量或网络层字节。不能把不同口径混用，更不能用隐藏修正倍率掩盖差异。
8. 同一份数据经过内部桥接、NAT、代理链或节点同步，不得重复扣量。
9. 处理累计计数器重置、进程重启、重复上报、乱序、并发更新、数据库恢复及 client 删除后重建。
10. 计量游标、原始累计值、已计费值和必要的事件标识必须具有一致的持久化语义。
11. 旧数据迁移到默认倍率 1 时保留已有用量，不清零、不重复扣费。
12. 限速基于明确的原始速率口径，不能因为计费倍率为 2 就意外把实际带宽减半。
13. 已有多节点场景必须防止节点和主面板重复乘倍率或重复累计同一上报。

额度执行：
- 额度耗尽后拒绝新连接，并终止或阻断该 client 的已有连接和持续 UDP 流。
- 不能只将数据库中的 enable 改为 false。
- 重启面板、后端或服务器后，不能恢复已耗尽用户的访问。
- 降低额度至已用量以下时，也必须执行限制。
- 续期、重置或增加额度时，只解除对应限制原因；不能意外恢复仍被人工禁用或已经到期的用户。
- 给出封禁延迟、在途数据、采样误差和最大超用量的明确上界，并通过测试验证。
- 不得用“零超用”的口号代替数据面实现，也不得在测试失败后任意放宽容差。

八、端口转发作为一等服务类型

在现有创建、分配和客户端管理流程中加入端口转发，使其与代理协议一样可选择、可管理。

不要另做一个只负责执行 shell 命令的独立页面。

至少支持：
- TCP、UDP，以及同一业务需要的 TCP+UDP 配置。
- 监听地址、监听端口、目标地址、目标端口。
- IPv4 和 IPv6 的适用转发场景。
- client 归属、备注、启停、来源访问控制。
- 每个 client 的上传/下载限速、倍率、额度、到期、统计和超额断流。

用户归属：
1. 普通端口转发没有协议级账号认证，必须显式建立转发资源到 client ID 的归属。
2. 默认以独占的“节点 + 传输协议 + 监听地址 + 监听端口”绑定一个 client；同一 client 可拥有多条规则。
3. 同一 client 的多条规则必须合计限速和扣量。
4. 不得仅凭源 IP 识别用户，也不得把无法区分归属的共享监听端口标成独立用户服务。
5. 展示并检查资源冲突；删除后重新分配的端口不能继承上一用户的统计或策略。

后端选择：
优先评估 nftables；仅在兼容性或实际环境有充分理由时选择 iptables。记录原生 nftables、iptables-nft、iptables-legacy 及现有防火墙的情况，避免混用造成重复规则和重复计费。

执行要求：
- 转发、计量、限速、额度控制必须形成完整数据路径；NAT 规则本身不能替代后几项能力。
- 在能够覆盖完整流量的位置计数，不能依赖只经过连接首包的 NAT 规则。
- 正确处理回程、SNAT、conntrack、标记恢复和长连接。
- 超额禁用必须作用于已建立连接，不能被 established/related 放行规则绕过。
- 验证 flow offload 等加速路径是否绕过计量或执行；对受管流量采取明确措施。
- 明确内核直转与进入统一代理路由的区别。需要使用应用层路由或代理出站时，必须有真实桥接路径并测试。
- 目标支持域名时，设计解析、刷新、地址变更和已有连接的处理方式。
- 不得把普通双栈支持宣称为已经实现跨地址族转换。

系统安全：
- 只管理带项目/实例标识的专属规则、链、集合、标记及 tc 资源。
- 禁止 flush 全局 ruleset、清空全部 iptables、重置全局 qdisc 或修改默认策略来简化实现。
- 不得破坏现有管理 SSH、面板访问、Docker、UFW、firewalld、Fail2ban 和无关业务。
- 配置先校验再应用；使用可实现的事务、补偿和状态核对机制处理部分失败。
- 添加、删除、重启恢复必须幂等，不能重复建规则或重复扣量。
- 失败和卸载时只清理自身资源。
- 内核和网络测试放在隔离环境中，不直接改动开发宿主机的管理网络。

九、前后端、部署与兼容性

所有功能必须贯穿：
数据库 → 服务层 → API → 前端 → 运行后端 → 统计与限制 → 备份恢复 → 安装升级。

具体要求：
1. 遵循现有组件、权限、错误处理和国际化规范。至少完成中文和英文新增文案，其他语言采用项目既有回退机制。
2. API 与前端字段、单位、校验和状态一致；敏感字段不得被日志或非授权接口泄露。
3. 订阅和配置导出按真实客户端格式生成。目标客户端不支持时明确提示，不能伪造无法使用的协议节点。
4. 数据库迁移、备份恢复、导入导出、批量操作及多节点同步不得漏掉新增字段和关联资源。
5. 根据项目实际支持情况验证数据库后端和打包方式，不能只在开发机运行。
6. 更新安装脚本、Docker 构建、依赖探测和升级流程。缺少权限、内核能力或后端程序时明确报错。
7. 非 Linux 平台不能执行 nftables/tc 等功能时应做能力门控，不得导致其他原有功能无法构建或运行。
8. 确保 fork 的安装或自动更新流程不会无提示地用官方版本覆盖本次定制。
9. 提供配置备份、升级、故障恢复和回滚说明；没有安全降级迁移时，说明如何使用备份恢复。
10. 不执行未经授权的生产环境部署、主机重启或全局网络变更。

十、测试与验收

先为关键语义和风险建立测试，再完成实现。不能修改预期结果来迁就错误实现，也不能将跳过测试包装成通过。

测试必须包含单元、集成和真实数据面端到端验证。

A. 计费与状态测试
- 倍率 0.5、1、1.5、2、10。
- 上传、下载和双向流量。
- 倍率切换前后的分段结算。
- 小包、高频采样、不同批次划分的结果一致性。
- 并发、重复/乱序上报、计数器重置和异常退出。
- 额度调整、重置、续期、人工禁用与到期状态的组合。
- 数据库迁移、备份恢复及旧数据兼容。
- 多节点同步和内部桥接不重复计费。

B. 限速端到端测试
- 每个现有及新增的适用协议使用真实客户端和真实数据路径验证。
- 覆盖单连接、多连接、上下行同时传输和多个 client 并发。
- 覆盖两个 client 共用公网 IP。
- 覆盖同一 client 多入站、多转发规则，以及适用的多节点场景。
- 在持续传输过程中修改限速，确认已有连接实际变化。
- 测试环境基线吞吐必须显著高于目标限速。
- 至少包含两个非零限速档位和不限速对照。
- 在排除启动阶段的持续测量窗口内验证上限，并结合已声明的有限 burst 计算允许偏差。
- 在健康、非竞争环境下验证实际吞吐不会长期明显低于配置值，不能把断流视为限速成功。
- 记录命令、客户端/后端版本、测量时长、实际吞吐和误差。

C. 额度端到端测试
- 使用便于复现的小额度，例如 100 MiB、倍率 2，验证原始计量流量约 50 MiB 时触发额度限制。
- 分别验证 0.5、1、1.5、2 等倍率。
- 在相同计量边界使用独立观测核对用量。
- 覆盖长 TCP 连接、持续 UDP、多连接抢占剩余额度和禁用后重连。
- 验证额度耗尽后已有流量停止、新连接失败、重启后仍受限。
- 报告真实封禁延迟和超用字节数，并与测试前确定的上界比较。
- 内部桥接不得造成 2 倍或更多的重复扣量。

D. 协议、路由与故障测试
- Snell v4/v5/v6 分别验证，不以一个版本通过代表全部通过。
- SSH 各已实现模式和 mieru 各适用传输分别验证。
- 覆盖认证失败、禁用凭据、目标不可达和端口冲突。
- 验证目标访问确实经过待测协议，不能让测速工具绕过代理后产生“通过”结果。
- 使用可观察的不同出口及目标，验证用户路由、域名/IP规则、阻断和出口选择。
- 杀死后端、重启面板、重建规则、模拟异常配置，检查恢复与策略执行。
- 验证无关用户和管理连接不受影响。
- 对原有协议和管理流程做回归测试。

E. 构建与静态检查
根据仓库真实工具链执行后端测试、适用的 race 检查、静态检查、前端测试与构建，以及相关打包验证。记录实际执行的命令和结果。

商业客户端、特定平台、root 权限或内核条件不具备时：
- 可以提供可复现的验证脚本或测试步骤。
- 必须标记“当前未执行/未验证”，说明缺少的条件。
- 不能用 mock 测试替代真实互操作测试后宣称完成。
- 不能将 CI 中的 skip 计入通过数量。

十一、执行顺序与交付物

建议顺序：
1. 仓库审计、版本核对、能力矩阵、架构方案和风险验证。
2. 统一 client 身份、计量、倍率、额度和限速基础设施。
3. 各协议逐个纵向实现：后端、API、前端、部署和对应测试一起完成。
4. 端口转发及防火墙/流控资源管理。
5. 订阅、多节点、备份恢复、升级等完整整合。
6. 全量回归、故障测试、文档和最终检查。

允许根据依赖关系调整顺序，但要记录理由。不要长期停留在只搭建接口、空实现或只改 UI 的阶段。

在仓库中维护以下文档，路径可遵循现有规范：
- 实施计划和完成状态。
- 协议/功能能力矩阵。
- 架构与数据路径说明。
- 限速、计量、倍率和额度的精确定义。
- 测试命令、环境、结果与未验证项。
- 安装、升级、恢复及回滚说明。

最终回复必须提供：
1. 实际使用的上游版本、基线 commit 和各后端版本。
2. 按需求逐项说明已完成、未完成、不适用及未验证内容。
3. 关键实现与数据路径，尤其是 client 身份、限速、计量和超额断流的位置。
4. 实际测试命令与结果，包括失败、跳过、容差和未具备的环境。
5. 关键 commits、远端分支和 push 核实结果。
6. 安装、升级、配置和回滚方式。
7. 剩余风险及阻塞原因。

只有功能实际工作、相关路径完成整合且验收有证据时，才能标记为完成。存在未解决的核心需求时，应明确说明当前交付边界，不得以“基本完成”“理论上支持”代替结果。
